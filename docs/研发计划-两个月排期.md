# 门诊多检查动态调度系统 · 已实现功能与两个月研发计划

> **范围**：算法内核、路线规划、挂号业务、双端与工程化，共约 9 周
> **排期口径**：两个月（9 周），每个阶段都有可验收的交付物

---

## 一、功能清单

> 1.1–1.3 已实现并验证；**1.4–1.5 待实现**，按计划安排在第 4–6 周（阶段二末至阶段三）。

### 1.1 算法内核（已实现）
- [x] 队列消退模型：`wait(t) = max(0, W0 − t)`，支持保守模式（不消退）
- [x] 取号模型：叫号时刻 = 现在 + 号差 × 人均服务时长；过号自动转「现场重取」
- [x] 精确求解器：分支限界 + 科室级可采纳下界（下界常等于最优值）
- [x] 正确性验证：120 组随机算例与暴力枚举对拍 + 独立模拟器二次验证
- [x] 约束支持：前置依赖（含报告等待）、时间窗、项目互斥
- [x] 次要目标：完成时间接近时优先保持推荐稳定（防抖动）
- [x] 规则库：检查项目与耦合规则独立成配置文件（`rules.py`）

### 1.2 路线规划业务（已实现）
- [x] 最优检查路线 + 预估时间轴（到达/等待/开始/结束）
- [x] 等待双口径：取号按号差精确计算，未取号按队列估算（上浮 15%）
- [x] 移动耗时计入（换科室 4 分钟，同科室一次到场不重复计）
- [x] 同科室合并：一次采血完成血常规+生化等多项
- [x] 取号提醒：等待空档判断「顺路取号来不来得及」
- [x] 路线解释：每步给出原因说明（为什么先做这项）

### 1.3 挂号业务（已实现）
- [x] 挂号页：每项显示当前叫号、排队人数、等待时长、取号后预计叫到时间
- [x] 一次挂多个号，点击先后即挂号顺序
- [x] 顺序校验（前缀判定）：偏离推荐弹窗确认，确认后按用户选择重排
- [x] 已挂号块重排：已挂号排最前（组内最优），未挂号在其后单独优化
- [x] 排不下逐项降级：只退必要的项，说明如实标注「赶得上号 / 号已过需重取」
- [x] 挂号强制前置：前置未挂号则依赖项锁定，前后端双重拦截

### 1.4 双端与科室（待实现）
- [ ] 医生端：按科室独立工作台，只显示本科室患者（服务端隔离，跨科室开单 403）
- [ ] 患者端：挂号 → 就诊 → 医嘱 → 路线，完整链路
- [ ] 科室划分：5 个检查科室，就诊号带科室前缀

### 1.5 数据与工程（待实现）
- [ ] 动态队列数据源：独立进程（模拟叫号），端口取数，路线自动重算
- [ ] 部署上线：nginx 反代 + systemd 服务，公网可访问
- [ ] 前后端分离、README、部署文档、代码托管
- [ ] 界面加固：静态资源版本号、build 标记、「已按挂号重排」徽标、分段标题
- [ ] 整体测试与验收：单元测试全过 + 线上关键场景复现

## 二、两个月研发计划（约 9 周）

> 按稳健节奏把各需求排入两个月的开发周期，避免「全部做完才知道对不对」。

### 2.1 阶段总览

```mermaid
flowchart LR
    P1["阶段一<br/>第 1–2 周<br/>需求分析与算法内核"] --> P2["阶段二<br/>第 3–4 周<br/>可视化 Demo 与动态数据"]
    P2 --> P3["阶段三<br/>第 5–6 周<br/>部署上线与双端/科室"]
    P3 --> P4["阶段四<br/>第 7–8 周<br/>挂号业务闭环"]
    P4 --> P5["阶段五<br/>第 9 周<br/>路线重排规则与验收"]
```

### 2.2 阶段一：需求分析与算法内核（第 1–2 周）

**目标**：把技术方案变成可验证的算法内核，先在命令行跑通。

| 任务 | 内容 |
|---|---|
| 需求分析 | 精读技术方案，明确输入输出、约束类型、求解目标 |
| 规则库设计 | 项目目录 + 耦合规则（前置/时间窗/互斥）独立成配置文件 |
| 队列建模 | 队列消退模型、取号叫号模型、等待双口径 |
| 求解器 | 分支限界 + 可采纳下界，支持约束剪枝 |
| 正确性验证 | 暴力枚举对拍（120 组随机算例）+ 独立模拟器二次验证 |

**交付物**：算法内核 + 验证报告 + CLI 演示
**验收标准**：对拍结果与穷举完全一致；前置依赖、时间窗约束全部通过测试

### 2.3 阶段二：可视化 Demo 与动态数据（第 3–4 周）

**目标**：让用户能自己点选检查、看到路线，并且路线随队列自动变化。

| 任务 | 内容 |
|---|---|
| 网页 Demo | 启动列出全部检查项，点选出最优路线 |
| 时间轴可视化 | 分段展示排队/检查/移动，带步骤序号与科室图例 |
| 队列模拟器 | 独立进程提供叫号数据（排队/等待/当前叫号），端口取数 |
| 动态重算 | 队列变化时路线自动刷新，无需手动重新计算 |

**交付物**：可交互 Demo（本地可跑）
**验收标准**：改变队列数据后路线自动更新；时间轴与列表一致

### 2.4 阶段三：部署上线与双端/科室（第 5–6 周）

**目标**：从 Demo 变成真正可用的网站，区分医生/患者，按科室组织。

| 任务 | 内容 |
|---|---|
| 部署 | 服务器环境、nginx 反代、systemd 服务、HTTPS |
| 工程管理 | 前后端分目录、README、部署文档、代码托管 |
| 双端分离 | 医生端开单、患者端按医嘱执行（患者不自选检查） |
| 科室划分 | 患者选科室挂号，医生按科室独立页面，服务端隔离 |

**交付物**：公网可访问的双端网站
**验收标准**：医生只能看到本科室患者；跨科室开单被拒绝；医嘱正确流转到患者端

### 2.5 阶段四：挂号业务闭环（第 7–8 周）

**目标**：把「取号」做成完整业务，覆盖挂号、叫号、顺序提醒。

| 任务 | 内容 |
|---|---|
| 取号与检查解耦 | 点项目不再取号，路线输出预估时间轴 |
| 挂号页 | 每项显示当前叫号/排队/取号后预计叫到时间，一次可挂多个 |
| 顺序校验 | 偏离推荐前缀时弹窗确认，确认后按用户选择重排 |
| 取号提醒 | 等待空档里提醒「顺路去取号」，含来不来得及的判据 |

**交付物**：完整挂号流程（挂号 → 叫号 → 做检查）
**验收标准**：挂号后路线按号重排；顺序偏离有提示；提醒判据合理

### 2.6 阶段五：路线重排规则与收尾验收（第 9 周）

**目标**：把号对路线的影响做成明确规则，完成整体验收。

| 任务 | 内容 |
|---|---|
| 已挂号块重排 | 已挂号排最前（组内最优），未挂号在其后单独优化 |
| 降级策略 | 排不下时只退必要的项，说明如实标注号能否赶上 |
| 挂号强制前置 | 前置未挂号则依赖项锁定，前后端双重拦截 |
| 界面加固 | 版本号、build 标记、「已重排」徽标、分段标题 |
| 整体验收 | 单元测试全过、线上场景复现、研发文档整理 |

**交付物**：V2 完整版 + 研发文档 + 验收报告
**验收标准**：21 项单测通过；关键场景（挂号重排、前置锁定、降级）线上可复现
